# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (lines 33-38) | **Grace period off-by-one check & missing timezone/overnight handling.** The starter computes `minutes = int((punch_in - start).total_seconds() / 60)` and checks `minutes > 10`. Per rule R2, late occurs only when punch-in is strictly more than 10:00 (600s) after shift start. | For shift `09:30`, punching in at `09:40:01` yields `(punch_in - start).total_seconds() = 601s`, floor `minutes = 10`. Checking `10 > 10` evaluates to `False`, returning `0` instead of `10`. Additionally, calling `.replace()` directly on `punch_in` fails for overnight shifts and timezone conversions (UTC vs IST). | Replaced with strict seconds comparison: `diff_sec = (punch_in - shift_start).total_seconds()`. If `diff_sec > 600`, return `int(diff_sec // 60)`, else `0`. Incorporated IST conversion and overnight shift calendar offsets. |
| 2 | `compute_work_hours` (lines 40-41) | **Banker's rounding & un-truncated seconds.** Built-in Python `round(..., 2)` uses IEEE 754 round-to-even (banker's rounding), violating rule R4 which strictly requires round half-up. Also did not truncate instants to whole seconds prior to computation (R1). | Input difference resulting in 9.125 hours rounds to 9.12 instead of 9.13. Millisecond fractions could also distort the second count. | Implemented integer second division `(punch_out_ms // 1000) - (punch_in_ms // 1000)` and used Python's `Decimal.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)`. |
| 3 | `compute_overtime` (lines 44-47) | **Missing 30-minute threshold, broken overnight shifts, & naive/aware tz mismatch.** Starter returns `max(0, minutes)` without enforcing the rule R3 minimum threshold of 30 minutes. Shift end was constructed on `date_str` without shifting day forward for overnight shifts. Naive vs aware subtraction also triggers `TypeError`. | An employee punching out 15 minutes after shift end received 15 minutes overtime instead of 0. For a 22:00-06:00 overnight shift, shift end was placed at 06:00 of day 1 instead of day 2. Subtracting offset-naive from offset-aware raised `TypeError`. | Enforced `minutes >= 30` threshold (returning `0` otherwise). Derived shift end dynamically from `calculate_shift_and_date` (adding 1 calendar day for overnight shifts). Unified UTC datetimes. |
| 4 | `GET /health` (lines 72-74) | **False readiness report.** Always returns `{"status": "ok"}` with HTTP 200 without verifying MongoDB connectivity. | Stopping the MongoDB daemon still resulted in HTTP 200 OK from `/health` instead of the mandated 503. | Added `client.admin.command("ping")`. If it fails or raises an exception, catch and return `HTTPException(503, "Database unavailable")`. |
| 5 | `POST /employees` (lines 78-85) | **Check-then-insert race condition & unvalidated fields.** Uses `find_one` followed by `insert_one`, creating a race window under concurrency. Missing field validations for `emp_code`, `email`, and equal shift times (`shift_start == shift_end`). Stored local naive datetime and returned unformatted datetime. | Parallel requests with identical `emp_code` both succeeded or crashed. Requests with `shift_start == "09:30"` and `shift_end == "09:30"` returned 201 instead of 422. Returned `created_at` as ISO string or dict rather than epoch ms integer. | Enforced database unique index on `emp_code` and caught `DuplicateKeyError` to return HTTP 409. Added Pydantic regex validators and cross-field validator (`shift_start != shift_end`). Serialized `created_at` to integer epoch ms. |
| 6 | `GET /employees` (lines 88-96) | **Off-by-one pagination bug, unfiltered total count, & missing sort.** Calculates `skip = page * page_size`, which on page 1 skips the first 20 records. `total` counted `{}` rather than applying the `department` filter. Query did not sort by `emp_code`. | Requesting `GET /employees?page=1` returned records 21-40 rather than 1-20. Filtering by department returned `total` of all employees in the DB. Result was unsorted. | Changed pagination skip to `(page - 1) * page_size`. Passed filter `q` into `count_documents(q)`. Added `.sort("emp_code", 1)`. Added min/max validation for `page` and `page_size`. |
| 7 | `POST /attendance/punch-in` (lines 99-122) | **Unhandled non-existent employee (500 crash), race condition, wrong date calculation, & non-contract `id`.** If `emp_code` does not exist, `emp` is `None` and accessing `emp["shift_start"]` raises `TypeError` (500). Race condition on punch-in allowed duplicate records. Local server date used instead of IST calendar date (R1). Appended non-contract `id` string. Allowed invalid status strings. | Calling punch-in for `"EMP9999"` crashed with 500 instead of 404. Concurrent requests for same date caused duplicate writes. Instants around midnight UTC were assigned to wrong IST date. Response contained forbidden `"id"` field. Passing `"ABSENT"` or `"LEAVE"` was accepted. | Added explicit 404 check when employee does not exist. Created unique compound index on `(emp_code, date)` and caught `DuplicateKeyError` to return 409. Implemented R1 IST date & overnight logic. Strictly formatted output to schema without `"id"` or `"_id"`. Validated status enum against `PresenceStatus`. |
| 8 | `GET /attendance` (lines 125-151) | **Unbounded memory exhaustion, missing secondary sort, unvalidated date range, & wrong types.** Fetches entire collection into memory with `list(db.attendance_logs.find(q))` and sorts in Python. Fails secondary sort by `emp_code` asc. Does not validate `date_from > date_to`. Returned BSON datetimes and non-contract `id`. | OOM or severe latency degradation on 100k records. Requesting `date_from=2026-07-10&date_to=2026-07-01` returned empty items instead of HTTP 422. Output items had `id` instead of conforming to `AttendanceRecord`. | Moved filtering, sorting `[("date", -1), ("emp_code", 1)]`, and pagination `.skip().limit()` directly into MongoDB cursor backed by indexes. Added 422 validation for `date_from > date_to`. Converted all BSON datetimes to epoch ms integers and removed `id`. |
| 9 | Startup & index initialization (lines 20-24) | **Missing database indexes.** Starter created zero indexes, relying only on default `_id`. | Concurrency tests on employee creation and punch-in failed. Explain plans on queries showed `COLLSCAN` across the dataset. | Implemented idempotent index creation on startup in FastAPI lifespan: unique `emp_code`, `(department, joined_on)`, unique `(emp_code, date)`, `(date, emp_code)`, `(emp_code, punch_in)`, `(date, late_minutes, emp_code)`, and `(status, date, emp_code)`. |
| 10 | Datetime conversion & boundary handling (lines 22, 102) | **Naive vs UTC timezone confusion.** Starter created default `MongoClient` without `tz_aware=True` and used `datetime.now()` and naive `datetime.fromtimestamp()`. | Converting between local server time, naive UTC, and IST caused offset discrepancies when deployed across different machine timezones. | Initialized `MongoClient(..., tz_aware=True)`. Truncated all incoming epoch milliseconds to whole seconds and consistently parsed to/from timezone-aware UTC and IST (`UTC+05:30`). |
| 11 | `serialize_instant` (line 174) | **Timestamp multiplication order loses sub-second BSON precision.** `int(dt_or_ms.timestamp()) * 1000` truncates the float to a whole-second integer *before* multiplying, so the result is always a multiple of 1000 ms — off by up to 999 ms for any stored BSON datetime that was written with sub-second precision (e.g. `$date: "2026-07-08T05:00:00.250Z"` returns 1752980400000 instead of 1752980400250). | A BSON datetime with milliseconds in MongoDB is returned with a value 0–999 ms too low; comparing it to the original `punched_at` timestamp fails equality. | Changed to `int(dt_or_ms.timestamp() * 1000)` — multiply first, truncate second — preserving full millisecond precision. |
| 12 | `build_trend_pipeline` — `$unionWith` with `$documents` sub-pipeline | **`$documents` is not valid inside `$unionWith.pipeline` in MongoDB 6.0.** The starter used `$unionWith` with a nested `$documents` stage to seed a gap-fill document. `$documents` is only a valid top-level aggregation pipeline stage (requires no `from` collection), and MongoDB rejects it inside a `$unionWith.pipeline` with a runtime error. | Running the `/analytics/departments/{department}/trend` endpoint on a department with zero attendance records in the requested range would raise a server-side `OperationFailure`, producing HTTP 500. | Removed the `$unionWith`/`$documents` trick entirely. `$densify` with explicit `bounds` fills all calendar days regardless of whether the initial `$match` produces any documents; `$ifNull` in the following `$project` handles the zero-record case gracefully. |

### Non-defects Examined and Retained

1. **Using `emp_code` instead of MongoDB `_id`**:
   The starter uses `emp_code` as the business key across all endpoints and queries. Examined whether an internal ObjectId lookup was required; confirmed that the contract and `DATA_MODEL.md` explicitly mandate `emp_code` as the immutable, customer-facing unique identifier and forbid exposing `_id` in requests or responses.
2. **Storing calendar dates and shift times as strings (`YYYY-MM-DD`, `HH:MM`)**:
   Examined whether these should be converted to BSON Date objects in MongoDB. Retained strings as documented in `DATA_MODEL.md` section 1 because calendar dates and shift times represent local IST calendar concepts; storing them as UTC timestamps would introduce unwanted timezone shift bugs and date boundary errors.
3. **Persisting derived fields (`work_hours`, `late_minutes`, `overtime_minutes`, `half_day`)**:
   Examined whether analytics should recompute these on the fly. Retained stored values as authoritative per `DATA_MODEL.md` section 3 ("Stored derived values are authoritative") so that analytics pipelines read indexed, persisted metrics without incurring recomputation overhead.
